01한눈에 보기

문제
동승자가 최대 4명이면 하차 순서가 24가지입니다. 순서마다 길찾기 API를 부르면 호출량과 비용이 커지고, 여러 동승자가 동시에 등록하면 정원·경로가 꼬일 수 있었습니다.
해결
시간·거리 행렬을 지점 수만큼만 조회해 로컬에서 순열을 비교하고, 트랜잭션 락·버전 비교로 동시 등록·수정 정합성을 보장했습니다.
결과
순서 비교 외부 호출을 24회에서 행렬 요청 5회로 줄였고, 웹·서버·차량 앱 전 구간을 혼자 구현해 Python 회귀 테스트 39개를 통과했습니다.

04주요 기능 개발

제가 직접 설계·구현한 부분입니다.

01하차 순서 최적화 엔진

  • Kakao Mobility 다중 출발지 API로 시간·거리 행렬 구성 후 itertools.permutations로 전 순서 로컬 비교
  • 10 km 반경 밖 누락 셀만 전체 길찾기로 보완
  • 우선 승객 지정 시 첫 순서를 고정해 비교 대상 24 → 6으로 축소

02세션 · 경로 API (Python)

  • 정원 4명 검사를 SQLite 트랜잭션 / PostgreSQL pg_advisory_xact_lock 안에서 수행
  • idempotency key + payload 해시로 재시도 요청 처리, 세션 version 비교로 오래된 요청은 409 + 스냅샷 재조회
  • 초대·운전자 토큰은 token_urlsafe(32)로 만들고 SHA-256 해시만 저장

03QR 모바일 웹

  • 동승자가 앱 설치 없이 QR로 이름·하차 지점 등록
  • 초대·참가 요청 IP당 분당 30회 제한 (429 + Retry-After)

04Pleos 차량 앱 (Kotlin / Compose)

  • 최적 순서에 따라 다음 목적지를 Pleos NaviHelper로 전달
  • 차량 속도·기어를 1초마다 조회해 정차(0.3 m/s 미만 + P 기어) 시에만 운전자 조작 허용, 신호 미수신 시 잠금
  • 운전자 토큰은 Android Keystore AES-GCM으로 암호화 보관, Gradle Mock / Pleos Flavor 분리

05기술적 의사결정

제약 조건 안에서 어떤 대안을 비교했고 왜 그 선택을 했는지 정리했습니다.

DECISION 01

순서마다 길찾기를 부르지 않고, 시간·거리 행렬을 한 번 만들어 로컬에서 비교

상황
Kakao Mobility API 사용 한도와 초과 요금. 동승자 최대 4명 → 하차 순서 4! = 24가지
선택지
A. 24개 순서마다 전체 길찾기 요청
B. 목적지당 다중 출발지 요청 1회로 행렬 구성 후 로컬 합산
결정
B. 출발지 포함 5개 지점 기준 행렬 요청 5회로 전 순서 평가. Kakao 실패 시 다른 제공자로 넘기지 않고 오류 반환(OSRM·Naver 분기 제거)
효과
외부 호출 수가 순서 수가 아닌 지점 수에 비례 → 24회 → 5회

DECISION 02

여러 동승자의 동시 등록·동시 수정 정합성 확보

상황
여러 명이 동시에 QR 등록하면 정원(4명) 초과·중복 등록, 운전자·동승자 동시 변경 시 경로 스냅샷 불일치 가능
결정
트랜잭션/advisory lock 안에서 정원 검사, idempotency key로 재시도 처리, 세션 version 비교 후 stale 요청은 409
효과
동시 요청에서도 정원·경로 상태가 일관되게 유지

06트러블슈팅

문제 → 원인 → 해결 → 결과 순서로 정리했습니다.

01하차 순서를 비교할 때마다 외부 API 호출이 폭증하던 문제

순서별로 전체 경로를 조회하면 순서 수만큼 외부 호출이 발생했습니다.

원인

  • 순서 수(24)에 비례한 외부 호출
  • 다중 출발지 API의 10 km 반경 제한으로 일부 구간 누락

해결

  • 목적지 단위 행렬 조회로 호출 수를 지점 수에 비례하도록 변경
  • 누락 셀만 선택적으로 보완 호출
  • 요청당 12초 타임아웃

결과

  • 순서 비교 외부 호출: 24회 개별 조회 → 행렬 요청 5회 (4명 기준)

02무료 도로 경로 요청이 HTTP 500으로 실패하고, 주행 중 조작 위험이 있던 문제

통행료 없는 경로를 요청하면 서버 오류가 났고, 운전자가 주행 중 화면을 조작할 수 있는 구조였습니다.

원인

  • 다중 경유지 API의 avoid 필드를 배열이 아닌 문자열로 전송
  • 주행 상태와 무관하게 운전자 화면 조작 가능

해결

  • avoid 필드를 배열 형식으로 수정, Kakao가 통행료 0원을 확인하지 않으면 무료 경로로 저장하지 않음
  • 차량 속도·기어 1초 주기 조회, 정차 + P 기어일 때만 조작 허용, 이동 중 동승자 수정·삭제 차단

결과

  • 무료 도로 경로 요청 HTTP 500 → 성공 (통행료 0원)
  • Python 회귀 테스트 39개 통과

07회고 · 개선 방향

현재 한계

행렬 요청을 목적지별로 순차 실행해 4명 기준 계산에 18.87초가 걸립니다(실 API 1회 측정). 요청 제한이 단일 프로세스 메모리 카운터라 다중 서버 환경을 지원하지 않습니다.
