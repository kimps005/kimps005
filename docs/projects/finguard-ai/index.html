01한눈에 보기

문제
금융 진단은 숫자 하나만 틀려도 리포트 전체의 신뢰를 잃습니다. LLM은 존재하지 않는 공시를 인용하거나 가격을 추정했고, 8 GB GPU 한 장으로 임베딩·리랭커를 서빙해야 했습니다.
해결
수치는 결정론적 Decimal 엔진이, LLM은 공시 해석만 맡도록 역할을 나누고, DOC-N 인용 검증·기업 범위 하이브리드 검색·데이터 소스별 장애 격리를 설계했습니다.
결과
LLM·데이터 소스가 전부 실패해도 결정론적 리포트로 SSE가 정상 종료됩니다. 단일 GPU에서 두 모델을 FP16으로 상주시키고, pytest 202개로 동작을 고정했습니다.
202pytest 테스트실행계획 · 연결 수 · 가드레일 회귀
32 → 5하이브리드 검색 후보 → 리랭킹벡터 + 형태소 랭킹
≤ 2.5 GB임베딩·리랭커 FP16 VRAM 상한초과 시 스모크 테스트 실패
0개임베딩 중 열린 DB 연결GPU 대기 중 풀 고갈 해결

RAGAS·지연시간 지표는 오프라인 dry-run 결과만 확보한 상태입니다.

04주요 기능 개발

제가 직접 설계·구현한 부분입니다.

01LangGraph 진단 그래프

  • Router → 시장 데이터 → Decimal 계산 → 종목 Worker ×3 (Send Fan-Out) → 가드레일 → Synthesizer 구조
  • Router 250 ms 초과 시 정규식 분류로 Fast Path
  • 역할별 다중 LLM 공급자 단계적 대체 (Qwen ↔ Gemini ↔ DashScope)

02DART 공시 ETL · 하이브리드 검색

  • 기업·기간 청크를 먼저 고정한 뒤 코사인 유사도를 전수 계산하고, Kiwi 형태소 GIN 랭킹과 합산
  • 후보 32개 → CrossEncoder 리랭킹 → 상위 5개
  • EXPLAIN 기반 테스트로 실행계획 고정

03GPU 임베딩 · 리랭킹 서빙

  • bge-m3·bge-reranker-v2-m3를 FP16으로 단일 8 GB GPU에 상주, workers=1로 중복 적재 방지
  • gpu_semaphore(1)로 GPU 호출 직렬화, 리랭킹 batch_size=8 분할

04Decimal 계산 엔진 · 인용 가드레일

  • 스코어카드·오버행 희석률·4분기 역산·PER/PBR·매수 시뮬레이션을 Decimal(prec=64, ROUND_HALF_UP) 순수 함수로 구현
  • LLM에는 14자리 공시번호 대신 DOC-N 별칭만 노출, 미등록 별칭이 든 문장은 제거
  • LLM 입력은 종목명·비중·수익률·점수·마스킹 공시로 제한 (계좌 금액·수량 외부 전송 금지)

05FastAPI SSE · Next.js PIN 프록시

  • status · token · done 프레임으로 진단 진행 상황 스트리밍
  • Next.js 14 프론트엔드와 PIN 프록시 구현

05기술적 의사결정

제약 조건 안에서 어떤 대안을 비교했고 왜 그 선택을 했는지 정리했습니다.

DECISION 01

LLM에게 숫자를 만들게 하지 않고, 결정론적 Decimal 엔진 + LLM은 공시 해석만

상황
수치 오류를 잡아낼 수 없으면 리포트 전체가 신뢰를 잃음. 계좌 금액·수량은 외부 LLM으로 보낼 수 없음
선택지
A. LLM 수치 생성 / float 연산
B. I/O 없는 순수 함수 Decimal(prec=64, ROUND_HALF_UP) 엔진
결정
B. 모든 수치를 Decimal 엔진으로 고정하고 API·SSE·Redis·프롬프트 전 경로를 단일 인코더로 문자열 직렬화. 확정되지 않은 값은 추정 없이 None
효과
수치는 항상 재현 가능하고, LLM 장애와 무관하게 정량 리포트 생성

DECISION 02

전역 벡터 검색 후 필터링 대신, 기업 범위 Exact Scan + 하이브리드 랭킹

상황
전역 ANN으로 상위 k개를 자른 뒤 기업 필터를 걸면 해당 기업 청크가 누락됨. 벡터 검색만으로는 CB·BW·보호예수 같은 정확한 용어를 놓침
결정
B-tree로 기업·기간 청크를 MATERIALIZED CTE에 먼저 고정 → 코사인 유사도 전수 계산 + Kiwi tsvector GIN 랭킹 합산 → 후보 32개 → 리랭킹 상위 5개
효과
기업 단위 재현율 손실 제거, 정확 용어 검색 보완

DECISION 03

LLM 하나에 의존하지 않고, 역할별 다중 공급자 단계적 대체

결정
Router(Qwen, 15초) / Worker(Qwen, 45초, 시간초과 1회 재시도, 403·429·할당량 시 Gemini 전환) / Synthesizer(Gemini, 60초, 503·504 시 지터 백오프 후 DashScope 대체)
효과
안전 필터 차단·빈 응답·스키마 불일치를 LLMUnavailable로 일원화, 로그 기록 전 API 키 마스킹

06트러블슈팅

문제 → 원인 → 해결 → 결과 순서로 정리했습니다.

01GPU를 기다리는 동안 DB 연결을 붙잡고 있어 연결 풀이 고갈되던 문제

짧은 요청까지 DB 연결을 얻지 못해 5초 획득 제한을 넘기며 실패했습니다.

원인

  • 요청마다 새 DB 연결을 만들어 연결 수 무제한 → 풀(max 8) 도입
  • 트랜잭션 안에서 gpu_semaphore(1) 임베딩을 기다리며 연결이 idle in transaction 상태로 점유
  • asyncio 취소 시 GPU 스레드가 아직 실행 중인데 permit이 먼저 반환

해결

  • 임베딩·토큰화를 트랜잭션 밖에서 먼저 끝낸 뒤 executemany 단일 트랜잭션으로 적재
  • GPU 호출을 asyncio.shield로 감싸고, 스레드가 실제로 끝날 때 permit 반환
  • workers=1 고정, 리랭킹 batch_size=8 분할

결과

  • 임베딩 호출 시점에 열린 DB 연결 0개 (회귀 테스트로 고정)
  • 두 모델 FP16 VRAM 2.5 GB 초과 시 스모크 테스트 실패 처리

02데이터 소스 하나만 실패해도 진단 전체가 멈추고, LLM이 없는 공시를 인용하던 문제

한 종목의 수집 실패가 전체 진단을 취소시켰고, LLM은 존재하지 않는 공시번호를 인용하거나 가격을 추정했습니다.

원인

  • 전 종목 수집을 asyncio.TaskGroup 하나로 묶어 하나의 예외가 전체를 취소
  • DART 적재 시간 제한 부재
  • LLM의 환각 인용·가격 추정

해결

  • optional() 헬퍼로 소스별 실패를 격리하고 해당 점수만 미산정·경고, 잔고·종목 마스터 실패만 치명 오류
  • DART 적재 15초 타임아웃 + 공시 단위 커밋으로 부분 적재 보존
  • DOC-N 별칭만 노출하고 Kiwi 문장 분리 후 미등록 별칭·원시 공시번호 포함 문장 제거, 가격 수치 근거 문장 폐기

결과

  • 수급·DART·재무 동시 실패에도 진단 중단 → done(ok=true) + 정상 종목만 Fan-Out
  • PyKRX 첫 로그인 약 8초 대기를 요청 경로에서 300초 주기 백그라운드 갱신으로 이동

07회고 · 개선 방향

현재 한계

workers=1 + gpu_semaphore(1)로 단일 사용자를 전제로 설계해, 동시 사용자가 늘면 임베딩·리랭킹 대기열이 병목이 됩니다. RAGAS·지연시간 지표는 오프라인 dry-run만 확보했습니다.

다음 단계

임베딩·리랭커를 Triton 등 별도 추론 서버로 분리해 Dynamic Batching 적용, API 프로세스 수평 확장, 공시 인제스트를 Redis 큐 기반 비동기 워커로 이전
