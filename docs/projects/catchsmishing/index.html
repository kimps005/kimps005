01한눈에 보기

문제
스미싱은 텍스트·캡처 이미지·QR 등 형태가 다양하고, GPU 없는 서버에서 빠르게 판정해야 했습니다. 외부 AI(Gemini) API가 실패하거나 키가 없어도 결과는 반드시 돌려줘야 했습니다.
해결
OCR·QR 전처리 → INT8 양자화 KLUE BERT 분류 + 규칙 NLP + URL 위협 인텔리전스를 결합하고, 생성형 AI는 ‘보조 신호’로만 쓰는 하이브리드 파이프라인을 설계했습니다.
결과
모델 크기 58% 감소, CPU 추론 p50 지연 47% 단축. 데이터 누수를 막은 그룹 분할 평가에서 7개 유형 분류 정확도 96.18%를 기록했고, 외부 AI 장애 시에도 응답을 유지합니다.
−58%모델 파일 크기426.58 → 178.56 MiB
−47%p50 추론 지연370.97 → 196.40 ms
−51%p95 추론 지연449.58 → 220.32 ms
96.18%7개 유형 분류 정확도그룹 분할 · 3 seed 평균

지연·크기는 FP32 대비 INT8 동적 양자화 로컬 벤치마크(생성형 SMS 2,800건) 기준, 정확도는 120개 하위 유형 그룹 분할 평가 기준이며 실사용 탐지 성능과 구분합니다.

03시스템 아키텍처

  1. INPUT문자 텍스트 · 캡처 이미지 · QR
  2. PRE-PROCESSOCR · QR 디코딩 · URL 정규화GUARDRAIL 입력 한도 · SSRF 차단
  3. INFERENCEKLUE BERT 7종 분류 · 규칙 NLP · URL 평판BOTTLENECK CPU 추론 · 외부 API
  4. VERIFYGemini 문맥 · Vision 보조 신호GUARDRAIL 실패 시 null 처리
  5. SERVE0–10 점수 · 등급 · 탐지 근거 JSON
GUARDRAIL 안정성 장치BOTTLENECK 성능 병목 지점
  • 이미지·텍스트·QR 입력을 OCR·QR 디코딩·URL 추출로 하나의 텍스트/URL 집합으로 정규화합니다.
  • INT8 KLUE BERT 카테고리, 규칙 기반 긴박·위협·행동 유도 패턴, URL 피드·VirusTotal·WHOIS·APK 신호를 병렬로 계산합니다.
  • Gemini 문맥·Vision 점수는 사용 가능할 때만 결합하고, 입력 유형과 신호 가용성에 따라 가중치를 분기해 최종 등급(0–10점)을 산출합니다.

04주요 기능 개발

제가 직접 설계·구현한 부분입니다.

01입력 전처리 (OCR · QR)

  • PaddleOCR·OpenCV·pyzbar로 캡처 이미지와 QR을 텍스트·URL로 변환
  • 텍스트와 URL이 모두 추출되지 않으면 추측하지 않고 Unknown + ocr_failed로 명시적으로 반환
  • 이미지 10 MiB·25,000,000 px, 텍스트 20,000자, 요청당 URL 10개로 입력 상한을 둬 악성·과대 입력 차단

02문자 유형 분류 모델 (KLUE BERT)

  • 스미싱 문자를 7개 유형으로 분류하는 KLUE BERT 모델 학습
  • 무작위 분할에서 같은 문장이 학습·평가에 동시에 들어갈 수 있는 데이터 누수를 발견 → 120개 하위 유형 기준 그룹 분할, 증강 데이터는 학습에만 사용
  • 3회 시드 평균 정확도 96.18%, Macro-F1 96.15%
  • INT8 동적 양자화 후 Hugging Face Hub에 배포 (정확도 손실 −0.11%p)

03URL 보안 분석기

  • URLhaus·Phishing.Database 피드, VirusTotal, WHOIS, APK 신호를 종합해 URL 평판 산출
  • 리다이렉트를 최대 5회까지 따라가며 단계마다 사설·루프백·링크-로컬 IP와 인증정보 포함 URL을 차단 (SSRF 방어)
  • VirusTotal 미등록 URL은 ‘안전’이 아닌 ‘정보 부족’으로 처리
  • 위협 피드 6시간 주기 갱신, 위험 URL 상위 항목은 주간 재검사

04통합 분석 API · 클라이언트

  • FastAPI 파이프라인에서 모든 신호를 모아 점수·등급·탐지 근거를 JSON으로 반환
  • 분석 작업을 최대 4개 ThreadPoolExecutor 워커로 격리하고, X-Analysis-ID로 진행 중인 분석의 협력 취소 지원
  • Flutter 클라이언트에서 문자·이미지·QR 입력과 결과 화면 구현

05기술적 의사결정

제약 조건 안에서 어떤 대안을 비교했고 왜 그 선택을 했는지 정리했습니다.

DECISION 01

생성형 AI 하나에 판정을 맡기지 않고, 경량 분류 모델 + 규칙 + URL 평판을 결합

상황
GPU 없이 CPU로 서빙해야 하고, Gemini·VirusTotal은 키 미설정이나 호출 실패가 언제든 발생할 수 있음
선택지
A. Gemini 단일 판정
B. 로컬 KLUE BERT + 규칙 NLP + URL 위협 인텔리전스 + Gemini 보조 신호
결정
B. 카테고리 판단은 로컬 INT8 모델로 고정하고, 생성형 AI는 보조 점수(P_Gemini·P_VLM)로만 결합
효과
Gemini가 없어도 OCR·규칙·URL 결과만으로 응답 가능. INT8 전환의 정확도 손실은 −0.11%p에 그치면서 지연은 절반으로 감소

DECISION 02

대용량 가중치는 저장소 밖에 두고, 버전을 고정해 내려받기

상황
대용량 모델 가중치를 Git 저장소에 넣을 수 없고, 위협 피드·악성 URL 정보는 시간이 지나면 낡음
결정
서버 기동 시 로컬 캐시를 먼저 확인하고, 없으면 Hugging Face에서 INT8 가중치·config·tokenizer만 다운로드. revision을 커밋 해시로 고정해 재현성 확보
효과
배포 환경마다 같은 모델 버전 보장. 위협 피드는 6시간 주기로 갱신하고 위험 URL 랭킹 상위 항목은 주간 재검사

06트러블슈팅

문제 → 원인 → 해결 → 결과 순서로 정리했습니다.

01CPU 서버에서 문자 1건 분석에 0.37초가 걸려 동시 요청을 버티기 어려웠던 문제

공개 API로 서비스할 때 여러 요청이 몰리면 응답이 크게 지연될 수 있었습니다.

원인

  • FP32 BERT 체크포인트가 426.58 MiB로 무겁고, 단일 메시지 추론이 p50 370.97 ms / p95 449.58 ms

해결

  • PyTorch INT8 동적 양자화 state_dict로 배포
  • 분석 작업을 최대 4개 ThreadPoolExecutor 워커로 격리하고 X-Analysis-ID 기반 협력 취소 지원
  • IP·경로별 요청 제한 적용 (이미지 10회/분, 텍스트 30회/분, 피드백 20회/분)

결과

  • 모델 크기 426.58 → 178.56 MiB (−58.14%)
  • p50 370.97 → 196.40 ms (−47.1%)
  • p95 449.58 → 220.32 ms (−51.0%)

02외부 AI·OCR이 실패하거나, 악성 URL이 내부망을 노릴 수 있던 문제

여러 외부 신호에 의존하는 구조라, 하나라도 실패하면 판정이 틀어지거나 서버가 공격 경로가 될 수 있었습니다.

원인

  • OCR 인식 실패, Gemini 호출 실패·미설정
  • 분류 모델의 확률이 곧 ‘스미싱일 확률’은 아님
  • 악성 URL을 추적하다 서버가 내부망으로 요청을 보낼 위험(SSRF)

해결

  • 텍스트·URL 모두 추출 실패 시 Unknown + ocr_failed 반환
  • Gemini 점수는 null로 처리하고 사용 가능한 신호만으로 가중치 분기
  • URL 강한 의심·정부기관 사칭 조건이면 등급 하한 보정
  • 리다이렉트 최대 5회, 매 단계 사설·루프백·링크-로컬 IP 및 인증정보 포함 URL 차단

결과

  • 외부 AI 장애 시에도 OCR·규칙·URL 결과로 응답 유지
  • URL 추적 경로의 SSRF 차단

07회고 · 개선 방향
